# Long-horizon context and memory: benchmark readiness

Status: source review, no LHTB model trial or benchmark result. Existing coding
transfer and completed LongMemEval/reuse evidence remain separate.

[Long-Horizon-Terminal-Bench2.0](https://arxiv.org/abs/2610.14146) is a closer
candidate for sustained agent work than the current short coding diagnostics.
Its authors describe77 tasks, extended execution and intermediate verification.
The [released dataset](https://hub.harborframework.com/datasets/silrlab/long-horizon-terminal-bench-2.0)
uses a modified Harbor harness: its binary continuation feedback and stopping
behavior matter to comparability. Stock Harbor and a single native CLI call
cannot silently stand in for that procedure. Published author scores are prior
work, not TTGL observations or current cost quotes.

The source metadata, README, license and harness dependency declaration are
pinned in a private review receipt. Task solutions/hidden tests have not been
read in this screen. No benchmark source, container or package has been executed.
Before inference, select disjoint development/validation tasks using domain and
resource metadata, exclude every previously reserved task family, and freeze the
allocation without selecting on observed treatment outcomes. Review the exact
runtime and images, including native/OS components, and establish empty/reference
controls and the native Codex boundary with positive metering. Confirmed affected
components block execution under the user's policy; incomplete evidence alone
has the documented Codespace allowance, which is not security clearance.

The comparison should include normal continued full-context Codex, equal raw
history available through files, and each eligible persistent-memory system.
A reset-session diagnostic can isolate rediscovery but must not replace the
normal continued control or manufacture a memory advantage by withholding its
context. Equal relevant personal/project information goes to controls. Separate
optional unused memory availability from actual retrieval and verified use.
Preserve benchmark-defined binary feedback equally; never expose hidden failure
strings, patches or scalar grades when the protocol forbids them. Changes to
feedback or persistence define an explicitly adapted experiment, not an official
benchmark score.

Cost includes all controller/answering, extraction, update, ranking, summarizing,
recovery and integration inference. Measure actual cached/fresh/output buckets,
not retained characters or hypothetical uncached input. Observe full registered
horizons and actual reuse counts. Keep local CPU/embedding/loading time, unknown
hardware prices, subscription cash and research overhead separate. Report quality
and cost by task as well as pooled totals; lower tokens with higher modeled cost
fails efficiency, and lower cost with lost matched successes fails quality.

The existing reviewed MCP graph server offers a lightweight next memory system;
its persistence probe is not efficacy evidence. Graphiti remains under backend
review: the Kuzu option was rejected as unmaintained, and the FalkorDB Lite wheel
candidate is blocked by a known bundled Redis version finding. A maintained
patched deployment is required before execution. Neither backend was installed.
No new managed service or credentials are required for the currently running
coding panel; additional infrastructure choices will be documented before use.

The first runtime graph resolves102 packages but is blocked before installation:
LiteLLM's declared `filelock<4` constraint selects3.32.7, which matches13 current
OSV advisories. The reviewed advisories identify fixes in4.0.9 or4.2.1. A resolver
success is not approval to execute. Preserve this failed candidate and examine a
maintained compatible patched runtime; do not silently override its declared
constraint or claim the entire benchmark is permanently unavailable. No LHTB
model/image/harness execution has occurred.
